# OpenSim / Moco dinosaur feasibility — 20 September 2026

## C42 implementation update

The missing runtime is resolved: the official Moco sliding-mass example now solves. A shared planar torque-driven Tarbo prototype is implemented and undergoing mechanical review. See the [prototype implementation and limitations](MOCO_TARBO_PROTOTYPE.md). The archive findings below remain valid; the runtime failure described in the original research snapshot is historical.

## Decision

**An alternate Tarbo generated offline with OpenSim Moco is technically credible as a staged experiment. It is not a model swap or a ready-made dinosaur gait.** Keep the current shared engine and accepted animation assets intact. Use one reusable biomechanical model builder and optimizer, with anatomy and behavior differences in profiles. Tarbo would be the first test animal, not a separate species solver.

This investigation inspected actual downloaded archives and source code, and initialized two published animal models in OpenSim 4.6 on this Mac's native arm64 Python. A tiny official Moco optimization reached the solver but failed to load IPOPT because `libgfortran.5.dylib` is absent. Thus model loading is verified; local optimization and dinosaur prediction are **NOT YET VERIFIED**. No alternate Tarbo animation or Unity transfer was implemented in this research stage.

The archive audit and hashes are in [opensim-resource-audit.json](opensim-resource-audit.json). Third-party archives remain in task research storage, outside runtime imports and outside the Git deliverable. Inspection does not imply production reuse clearance.

## Corrections to the supplied investigation

1. **Moco and PredSim are not the same engine.** Both formulate optimal-control problems, but their implementation and model support differ. The Coelophysis supplement uses custom MATLAB/CasADi 3.4.5 and IPOPT 3.12.3 with OpenSim-derived dynamics; it is not a Moco template or a ready Moco study. The supplement README describes Windows and recompiling skeletal dynamics through Visual Studio. See Data S1 `OCP/PredSim_Coelophysis_Running_Muscles.m` and `ExternalFunctions/PredSim_Coelophysis_Run.cpp` in the [published supplement](https://www.ebi.ac.uk/europepmc/webservices/rest/PMC8457660/supplementaryFiles).
2. **An `.osim` is anatomy plus model components, not an automatic gait.** A prediction also needs actuation, contacts, states and control bounds, task/objective, initialization and solver configuration. OpenSim's [2D walking example](https://github.com/opensim-org/opensim-core/blob/4.6/Bindings/Python/examples/Moco/example2DWalking/example2DWalking.py) explicitly constructs tracking and predictive studies with periodicity and average-speed goals.
3. **Model substitution has constraints.** PredSim's preparation guide requires supported contact forces, replaces muscle formulations, does not support locked joints as-is and ignores coordinate constraints. It also calls out non-human bounds, limb definitions and hardcoded physiology. Do not load a legacy animal file and assume its original equations survive unchanged. [Model preparation](https://github.com/KULeuvenNeuromechanics/PredSim/blob/master/Documentation/ModelPreparation.md).
4. **Published model muscles are not necessarily known biological parameters.** Coelophysis prediction used a deliberately simplified active/passive muscle formulation because extinct muscle architecture is uncertain. Its axial joints used torque motors, and MTP reserves were allowed. Inspecting an `.osim` full of Millard muscles alone would misidentify the actual published predictor. [Bishop et al. 2021](https://pmc.ncbi.nlm.nih.gov/articles/PMC8457660/), supplement `MuscleModel/ForceEquilibrium_Simple.m`.

## What we should learn and reuse

The useful change is to solve coordinated motion under dynamic equations, contact and capacity constraints, rather than prescribing a knee curve and adding physics penalties afterward. In a Moco study, generalized coordinates and speeds, actuator/muscle states and controls evolve together. A target speed is a task; individual knee timing need not be prescribed. Contact force should arise from the contact model and its deformation, not from an independently fixed force schedule. [Moco methods](https://journals.plos.org/ploscompbiol/article?id=10.1371/journal.pcbi.1008493).

Coelophysis gives a concrete example of a movable axial system: trunk, neck/head and two tail regions, with leg-to-tail coupling through the caudofemoralis. Its result supports investigating lateral tail participation in angular momentum. It does not establish our particular figure-eight tail, its amplitude, or a multi-tonne tyrannosaur's run. The study also reports departures from extant expectations, so convergence alone is not validation. [Bishop et al. 2021](https://pmc.ncbi.nlm.nih.gov/articles/PMC8457660/).

For the feet, retain an articulated MTP/toe chain and several justified contact sites so load can transfer through the digits. A single contact sphere can be an economical first dynamics experiment, but cannot establish the material toe-roll behavior the user has worked to achieve. Whole-foot shape and pressure progression are part of the model, not decoration after the solve. PredSim's [toe-model study](https://doi.org/10.1371/journal.pone.0256311) is a useful methodology reference; its human parameter values are not dinosaur measurements.

Create one central biomechanics profile per admitted animal: segment lengths and frames; mass, COM and full inertia tensor per segment; joint freedoms and passive limits; muscle/actuator capacities and timescales; tendon assumptions; foot contact geometry/compliance/friction; movement tasks. Each number needs units, provenance, uncertainty and a label distinguishing measured, published estimate, comparative extrapolation and authored choice. Use the existing semantic rig/body/behavior data boundary, not a parallel species-specific configuration system.

## Proposed alternate Tarbo, before Unity

This is a proposed next experiment, not an implemented delivery.

**A. Establish a functioning offline reference.** Resolve the current wheel's missing GNU Fortran runtime in an isolated environment, rerun the official sliding-mass example and check its solution. Then run the official contact-bearing 2D walking example. Save exact package versions, solver settings and convergence/residual evidence. This establishes tool operation, not dinosaur realism.

**B. Build a Tarbo-calibrated reduced model.** Use T. rex anatomical relationships as comparative priors, then fit joint centers and segment proportions to the admitted Tarbo source and its specimen profile. Our profile uses a 2816.3 kg estimate for PIN 552-1; do not silently replace it with the mass of MOR555 or a larger T. rex. Start with explicit pelvis/trunk, head/neck, proximal/distal tail and two articulated legs including toes. Derive inertias from a documented volumetric approximation and test plausible mass/COM variations. An artist's surface mesh is not a fossil or a density measurement.

**C. First solve with transparent torque actuators.** This minimizes unsupported muscle assumptions and helps detect bad contacts, joint axes or mass distribution. Give internal joints bounded torque and activation response; keep the root unactuated except explicitly reported small diagnostic residuals. Optimize one periodic stride at a modest target speed, with smooth compliant ground contact, non-interpenetration, joint limits and reasonable effort/control-rate costs. Root support must come from the feet. Compare several initial guesses; a single local optimum is not evidence of a unique natural gait.

**D. Promote anatomy to a muscle-driven version only after calibration.** Use verified paths/moment arms from the T. rex material where homologous anatomy supports them. Replace the legacy 1.0 force entries with a sourced uncertainty model; identify or estimate fiber/tendon properties explicitly, or reproduce a documented simplified formulation. Add the caudofemoralis' mechanical connection to the tail. Do not describe the torque-driven first version as reconstructed dinosaur muscles.

**E. Let support duration be a result for the scientific candidate.** Do not force the current 14% airborne proportion into the alternate predictor. Test whether a feasible solution chooses flight at the selected speed and capacity. Large-tyrannosaur stress-limited research makes guaranteed aerial running a questionable premise; it is not a direct prohibition for our differently sized Tarbo. The model needs bone-loading limits if we want conclusions about stress—Moco will not infer them. Keep a game-authored aerial variant clearly labeled if artistic intent differs. [Sellers et al. 2017](https://doi.org/10.7717/peerj.3420).

**F. Review the mechanics before retargeting.** First deliver native-time side/front skeletal videos and a readable plot of knee angle, ground forces, COM and tail motion. Compare with the same-speed C39/C41 reference. Check forward replay consistency, mesh refinement, contact slip/penetration, dynamics residuals, reserve actuation, muscle/actuator saturation and sensitivity to uncertain mass/strength. These checks answer concrete visual/physical questions; they must not become another weeks-long validation framework before the first visible animal.

Suggested first success criterion: a repeatable contact-bearing Tarbo stride with visible load reception, push-off, recovery and forward reach, coupled torso/tail response, and reported physical residuals. Maximum sprint speed, impacts and arbitrary transitions are later checkpoints.

## Transfer to our rig and Unity, after review

Moco remains an **offline factory dependency**. Unity consumes baked motion plus the existing semantic metadata; mobile and desktop do not solve nonlinear optimal control every frame.

1. Export the solved states (`.sto`), controls, contact forces, model hash and coordinate definitions. Replay states through OpenSim and sample actual body transforms; never reinterpret raw generalized coordinates as Unity Euler angles.
2. Calibrate coordinate frames, handedness, units, joint centers and rest orientations into the existing semantic rig contract. A reduced tail joint maps to several art-rig bones by a documented distribution, not by matching bone names.
3. Retarget the whole chain while prioritizing pelvis/COM, knee and ankle trajectory, foot orientation and contact. Preserve the physical solution as a reference; measure how skin correction and rig proportion differences alter it. High retargeting error means revise the physical-to-art rig fit, not silently distort the dynamics.
4. Export through the existing factory motion contract, reopen the asset, then check Unity import parity and actual skinned contact. Current C41 Unity landmark mismatch remains a separate open issue; the adapter must not inherit a claim of parity from OpenSim.
5. Only after review, bake a small speed/turn family and transitions or use it to calibrate the shared runtime solver. One periodic Moco clip is not a reactive gameplay controller and does not solve hit-to-run transitions by itself.

## Reuse terms and environment evidence

- T. rex / Velociraptor Figshare datasets and Gracilisuchus metadata specify **CC BY 4.0**. The Velociraptor record explicitly excludes the included chapter PDF from that license. Keep attribution and record modifications.
- OpenSim core is **Apache-2.0**. PredSim is **AGPL-3.0**; do not treat its code as interchangeable with the Apache Moco codebase. Their dependency notices also matter if distributing tools.
- The Coelophysis article identifies **CC BY-NC 4.0**. The downloaded supplement README requests citation but supplies no separate permissive license statement. Direct production reuse of its code/model/output requires clarification; studying methods and writing an independently sourced implementation are separate decisions. Do not infer commercial permission merely from a public download.
- MuSkeMo's inspected tree has no root license file, and [issue 125](https://github.com/PashavanBijlert/MuSkeMo/issues/125) remains open. It can inform the workflow; code redistribution is not cleared by this investigation.

Local research environment: Python 3.12.10, OpenSim 4.6, native arm64, macOS 26.3. Both Coelophysis and Gracilisuchus initialize successfully. Missing visual geometry warnings during the lightweight load do not establish render readiness. The official `exampleSlidingMass.py` failed at IPOPT plugin loading due to `/opt/homebrew/opt/gcc/lib/gcc/current/libgfortran.5.dylib`; no optimized solution was produced. Current [OpenSim Python instructions](https://opensimconfluence.atlassian.net/wiki/spaces/OpenSim/pages/53085346/Scripting+in+Python) and [4.6 release notes](https://opensimconfluence.atlassian.net/wiki/spaces/OpenSim/pages/1274118147/Whats+New+in+OpenSim+4.6) supersede older x86-only guidance.

Research conclusion: proceed with a bounded Moco prototype after reviewing this proposal. The main work is a calibrated dynamic animal and a faithful rig adapter; Moco supplies the optimization machinery we should not reinvent. Neither this report nor a successful solve certifies how an extinct animal actually moved.
